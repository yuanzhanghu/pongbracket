1核心思路

今天的数据模型里，Team / Player 是「赛事内」实体，与登录账号 User 没有任何关联；权限只有「俱乐部级」。本需求的本质是引入一个跨赛事、由网站管理员维护的积分体系，并让账号能以「个人赛一人一队」的方式自助参赛：

新增核心实体 积分类别 (Rating Category)（全局，非俱乐部所有；默认「加华积分 CanadaChinaTT」）。每个账号在每个类别里有一个等级分。个人赛可挂靠到某类别；用户申请加入即自动创建与用户同名的队伍并绑定账号。比赛结果按开球网 ChinaTT 规则逐场计算，但只有网站管理员赛后审核初始分通过后才真正结算升降。

体系围绕五个新概念，其余都是把它们接到现有结构上：

新概念作用归属 / 关联
Rating Category 积分类别跨赛事的积分池（加华积分…）全局，仅网站管理员维护
Player Rating 账号等级分(账号 × 类别) → 当前分 / 初始分 / 审核状态关联 User
Team↔Account 绑定让比赛结果落到账号头上个人赛申请时自动建同名队伍，1:1
Join Request 参赛申请用户申请加入个人赛关联 Tournament ↔ User
Trusted Manager 托管管理员用户授权的管理员，可免审核直接拉人进赛关联 User ↔ User（被管理者 ↔ 管理员）

2关键约束与已定决策

决策结论
积分主体账号（个人）。比赛永远是「账号 vs 账号」。
计分范围仅个人赛（一队 = 一人）可计分，也仅个人赛允许个人账号申请加入。团体赛照常办赛，无积分 / 无申请入口。
队伍创建用户申请加入个人赛 → 自动创建与用户同名的队伍并 1:1 绑定该账号。
托管管理员用户加入比赛时可勾选「把创建者设为托管管理员」。每个用户维护一份托管管理员列表（可增删）；列表中的管理员下次可免该用户同意直接拉其进赛。
锋利边缘：在某一个赛事入会时勾一次，等于授予该创建者一项永久、对其今后所有个人赛生效的权限升级，藏在勾选框后很易被忽视。入会处文案必须写明「永久、对该创建者的所有未来个人赛生效」；「我的托管管理员」页可随时撤销（已含）。可选增强：给授权加作用域 / 到期限定。
计分粒度整赛事一个批次（batch-per-event）：赛事内每场都用选手「入场前冻结分」查表算 delta 再求和，赛内顺序不影响结果；赛事之间按结算顺序（settled_seq）依次叠加。
预排名初始分创建者在队伍预排名时，可给无积分的账号 / 队伍指定一个临时初始分；队伍排名按初始分自动排序，用于蛇形分组。
升降结算门槛创建者赛后点「申请积分结算」（校验全员已绑账号）→ 网站管理员审核新人临时初始分通过后，系统才批量结算升降。审核前积分「冻结」，仅用于分组排序。
结算资格强制全员绑定账号：rated 个人赛必须所有队伍都绑定账号才允许「申请结算」；未绑定者拦在结算入口（提示创建者补绑）。
「录入积分」权限= 赛事级记分员：被授权账号可在该个人赛录 / 改比分；不开放手改等级分。
积分类别归属网站管理员创建与维护，不属于任何俱乐部。需新增全局管理员角色。
「一队一人」如何保证个人赛建队 / 加人入口强制 team 的 player 数 = 1（自动建队即满足）；rating 始终以 team 为单位结算，与队内人数解耦。现有 /teams、/players 接口在个人赛下须加该校验，防止绕过。
结算时机（无「已结束」态）现 TournamentStatus 仅 OPEN / ARCHIVED。「申请结算」判据 = 该赛事「已成形对局」全部录得胜负：非 draft 轮里凡两侧已物化为 Final team 且双方已绑账号的场（MatchWithDetailsDefinitive）不得存在 score1==score2（含 0–0）（判据细节与「为何不能直接用『计分场次』判完整」见 §3）。不另加状态机；owner 任意时点可点，后端按此校验。

3数据模型

沿用现有「原生 SQL + Pydantic + Alembic」模式（backend/bracket/schema.py、backend/bracket/sql/*、backend/alembic/versions/*）。新增 6 张表，给 tournaments 加 2 列、users 加 1 列。

新增 全局管理员标识 —— users 加列

users.is_admin   BOOLEAN  NOT NULL  DEFAULT false   -- 网站管理员：维护积分类别、审核初始分

替代方案：扩展 account_type 枚举出 ADMIN。但 is_admin 布尔列与 DEMO 账号正交、改动最小，推荐布尔列。

新增 rating_categories —— 积分类别（全局）

id, key UNIQUE ('CanadaChinaTT'), name ('加华积分'),
algorithm DEFAULT 'chinatt', created          -- 无 club_id，全局共享

迁移时 seed 默认：key='CanadaChinaTT', name='加华积分', algorithm='chinatt'。

新增 player_ratings —— 账号在某类别的等级分（ledger head）

id, category_id FK, user_id FK,
initial_rating  Integer,         -- 创建者预排名时给的临时初始分
current_rating  Integer,         -- 审核+结算后的正式分（审核前=初始分，仅供排序）
status          Enum('PENDING','ACTIVE'),   -- PENDING=初始分待管理员审核
approved_by     FK users NULL,   approved_at DateTimeTZ NULL,
matches_played  Integer DEFAULT 0,  last_updated DateTimeTZ
UNIQUE(category_id, user_id)
等级分用整数，不用 Numeric。ChinaTT 表的查表键是两选手分差（整数），产出也全是整数档（8/7/10…），且 §11 闭区间取档（diff ≤ 12 / 13 ≤ diff ≤ 37）对小数无定义。故 initial_rating / current_rating 一律整数：创建者填初始分、管理员审核调整、引擎 delta 均为整数，杜绝 diff = 12.5 落档歧义。不复用 per-tournament ELO 的 Decimal + int(K·…) 截断路径（calculation.py:58），与 elo_score 体系彻底解耦。

新增 rating_events —— 每场计分比赛的加减分流水（append-only）

id, category_id FK, match_id FK, user_id FK, opponent_id FK,
rating_before, rating_after, delta, result Enum('W','L'),
tournament_id FK,     -- 该流水属于哪个赛事批次（排序按其 settled_seq）
created DateTimeTZ     -- 结算写入时间（审计用，非排序键）

可审计、可重算：正式分 = 初始分 + Σ(delta)，按赛事 settled_seq 顺序叠加（赛内各场无序求和）；改已结算赛事的比分时，从该 settled_seq 往后重建本表（重放范围见 §5）。

user_id / opponent_id 是结算时解析出来的派生值，不是比赛自带字段。 见下「比赛 → 账号 解析层」：rating_events 仅 match_id 是原生外键，两个账号由结算引擎按解析路径推出后落库（落库后冻结，作为审计快照）。

关键 比赛 → 账号 解析层（matches 不直接连 team / 账号）

现模型里 matches 不引用 teams，而是引用 stage_item_inputs。一个 input 有三态：

input 态含义能否解析出账号
Final有 team_id，真正的队伍能（team → teams_x_users → user）
Tentativewinner_from_stage_item_id + winner_position 占位（指向上游 stage item 的名次），尚无 team_id不能 → 跳过
Empty轮空（bye）不能 → 跳过

解析路径：match → input1/input2（须均 Final）→ team_id → teams_x_users → user_id。代码已有 MatchWithDetailsDefinitive（两侧 input 均为非空对象）这一类型，结算引擎直接复用它判定「已成形的对局」。注意 Definitive 类型本身只要求两侧 input 行非空、并不保证两侧都是 Final team：一个 Empty（轮空）input 也是已填充但 team_id=None 的行（stage_item_inputs.py:63），故 Final+Empty 的轮空场同样会算成 Definitive。轮空被过滤掉不是靠类型、而是靠「双方已绑账号」那一条（Empty 无 team 可绑）。落地时务必保留绑定校验，不可因「已是 Definitive」就省掉它。

注：淘汰赛后续轮的占位是另一机制——match 级 winner_from_match_id（stage_item_input1/2_winner_from_match_id），此时 match 的 input_id 为空、非 Definitive，同样天然挡住提前结算。上面「input 三态」表描述的是 stage_item_inputs 行自身的状态（其 Tentative 态由 winner_from_stage_item_id 触发，用于跨 stage 种子）。

「计分场次」判据（结算引擎据此筛选，解决无 status 列问题）。 matches 表没有「已打完」状态，新建即 0–0，且淘汰赛会预先把整张签表的占位场全建出来。 故一场比赛纳入结算当且仅当同时满足：
  1. 所在轮 round.is_draft = false；
  2. 是 MatchWithDetailsDefinitive（两侧 input 都已物化为 Final team）；
  3. 两队都已绑账号（teams_x_users 命中）；
  4. 比分可判胜负 score1 ≠ score2（乒乓无平局，0–0 ＝ 未打 ＝ 跳过）。
轮空、单侧空位、占位未物化、未录分的 0–0 一律不计。引擎只产出 W/L，无平局 / 弃权分支。

「计分场次」≠「完整性判据」（修正循环定义，否则可半场结算）。上面四条是结算时把哪些场计入的过滤器，不能反过来判断「赛事是否打完」——未打的 0–0 按定义就被排除，用它判完整是自我空转，永远发现不了还有没打的场。淘汰赛靠 Tentative 占位天然挡住提前结算；但 round-robin / Swiss 开赛即把整组建为 Definitive + Final + 0–0，过滤器会把未打的场当「非计分场次」跳过，于是打一半即可申请结算、剩余场被静默丢弃，等它们补打完只能落到更大的 settled_seq → 被迫改已结算赛事 → 触发链中段重放（§4/§5 最贵路径）。
故结算完整性闸门另立判据（与「计分场次」过滤器分开）：非 draft 轮里，凡两侧已物化为 Final team 且双方已绑账号的「已成形对局」，一律不得存在 score1==score2。即区分两种 0–0：占位未物化（Tentative/Empty，正常跳过）vs 已成形但未录分（Definitive + 已绑 + 0–0，阻断结算并提示「还有未录分的比赛」）。
另须查「尚未生成」的场：上面只能看到已存在的 Definitive 场，但 Swiss 后续轮是 draft 轮、按需才建（create_match 仅允许在 Swiss 的 draft 轮建场，routes/matches.py），多阶段赛的后续 stage 未激活前也无 match 行。只查 0–0 会漏判：第一轮打完、后续轮尚未 draft 时闸门误判「已完整」。故须叠加结构性完整判据——该 stage item 无残留 draft 轮、Swiss 处于终态、且整个赛事的 stage 推进已到末。
「无未激活的后续 stage」须按真实 schema 表达——没有「本 stage 已完成」标志，只有单一 is_active 指针。sql_activate_next_stage 做的是 SET is_active = (stages.id = :new_active_stage_id)（sql/stages.py:205）：全表同时只有一个 stage 是 active，已打完的早期 stage 同样是 is_active=false，与「尚未激活的后续 stage」无法用 is_active 区分。故完整性判据须改成可判定的形式：当前 active 的 stage 必须是最后一个 stage（max(stages.id) / 末位 order），且其下所有 Definitive+已绑场均已判胜负；或为赛事引入一个真正的「计分完成」标志位，不可依赖「后续 stage 未激活」这种不可表达的判据。
另：已结算赛事禁止向前回拨 stage。反向激活（direction="previous"）走 update_matches_in_deactivated_stage（handle_stage_activation.py:200-211），它对被离开 stage 的每个 stage-item 做两件相互独立的写：(a) clear_scores_for_matches_in_stage_item 把比分清零（sql/matches.py:261，只 SET score1=score2=0, games=NULL，不动 team_id）；(b) 单独对其中 winner_from_stage_item_id IS NOT NULL 的 tentative input 把 team_id 置空（仅跨 stage-item 种子的占位，非全部 team_id）。若赛事已结算后再回拨 stage，比分被清零会让账本（rating_events）与实时比分脱节。故 settled_seq IS NOT NULL 的赛事必须禁止任何 stage 反向激活——守卫挂在 direction="previous" 的激活入口（非两个底层 helper 之一，二者是分开的两次写），要改须先走管理员级「撤销结算」。同理，已结算冻结须一并覆盖 stage-item（及 stage）的删除，不能只挡 direction="previous" 一条路径。真正抽空账本 match 祖先的是 stage-item 删除（DELETE /stage_items/{id} → sql_delete_stage_item_with_foreign_keys 按序删 matches→inputs→rounds→stage_item，sql/shared.py）；删 stage 路由本身会拒绝删非空 stage（须先删其 stage-item），故冻结的着力点主要在 stage-item 删除，stage 删除一并挡住即可。

录分即校验可判胜负（防平局静默丢失）。rated 个人赛的已成形对局录分时，最终比分必须可判胜负（score1≠score2）；误录成平局（如 3–3）应当场拒绝，不能让它沿用「0–0 ＝ 未打」的语义被静默从积分里漏掉。get_winner() 平局返 None 只承载「未打」语义，不可当作「已打平」的有效结果。
校验落点：录分的唯一写入口是类型无关的共享路由（PUT /matches/{id} → sql_update_match，团体赛 / 个人赛共用），故该校验须落在共享写路径内、并以 is_individual AND rating_category_id IS NOT NULL 为门控，否则要么误伤团体赛（团体赛允许平局），要么被从共享路由绕过。
门控字段是可变的——翻 flag 时须回补校验。is_individual / rating_category_id 可经 PUT /tournaments/{id} 事后改写：赛事先以非积分态录分（match 新建即 0–0，可遗留已成形但未录分的 0–0，甚至误录平局），再翻成积分态，则这些行录入时门控为假、从未被校验过。下游虽有「结算完整性闸门」兜底（任何 Definitive+已绑的 score1==score2 都会阻断结算而非静默丢分），但报错会显示为「还有未录分的比赛」、令人困惑。故 PUT /tournaments/{id} 把赛事转入积分态（is_individual ∧ rating_category_id 由假变真）这一步，必须同步回扫所有已存在的 Definitive+已绑场、对 score1==score2 当场拒绝翻 flag，把门控漏洞在转入边界补上。

现有「赛事内排名」模块仍把 0–0 当真平局——须显式与 rating 解耦。本设计把 0–0 视作「未打」跳过，但同一批 match 行还喂给现有排名 / 积分榜逻辑：logic/ranking/calculation.py:29 用 was_draw = (score1==score2) 记一次平局并给 draw_points、draws+1。于是 round-robin 里一场未打的 0–0 在现有赛事内名次里已被当平局计入。两套语义对 0–0 的解释相反，须明确：跨赛事 rating 与现有 per-tournament standings 相互独立；并择一处理——要么把「未打的 0–0」也从现有 standings 排除，要么接受并文档化该差异（赛事内名次含未打场的「平局」）。

新增 账本完整性约束（防删 / 防改坏链）

结算后 rating_events 构成不可断的链，但现有接口仍能删赛事 / 队伍 / 账号（删 user 还会级联删其名下俱乐部 + 全部赛事）。需补：

  • 已结算实体禁删：settled_seq IS NOT NULL 的赛事，及其队伍、已 ACTIVE 的 player_ratings，删除接口一律拒绝；要删须先走管理员级「撤销结算」回滚账本。
  • rating_events 外键用 RESTRICT（或对 user_id / match_id / tournament_id 同时存审计快照值而非纯 FK），保证流水不会因上游删除而悬空。
  • 绑定（teams_x_users）锁定：仅 settled_seq IS NULL 时可增删改；结算后绑定锁定，如确需纠错须走管理员级撤销结算 / 重放（见 §5）。
光给 rating_events 加 FK RESTRICT 拦不住应用层级联删除。删 user 走的是 sql/users.py 的 delete_user_and_owned_clubs：它逐表先删赛事内容、再删赛事、再删俱乐部——轮到删某行时其 FK 约束可能已被前面的删除满足，RESTRICT 形同虚设。故「已结算实体禁删」必须挂在应用层删除路径上，但仅守 user 删除入口不够：真正抹掉账本祖先的是底层 sql_delete_tournament_completely（logic/tournaments.py，按序删 matches→…→teams→tournament，无 transaction），以及 delete_team（routes/teams.py，单独可孤立 teams_x_users / rating_events.user_id）。故 settled_seq IS NOT NULL 守卫须挂在每条删除路径的入口（删任何子行之前），而非寄望某个「最低共享函数」——删赛事有两条互不相交的路径：DELETE /tournaments/{id} 路由直接走浅删 sql_delete_tournament（routes/tournaments.py:135，单行删除、不连带子表），而 user 级联走 sql_delete_tournament_completely（仅 sql/users.py:134 调用，先逐层删 matches…teams 再 sql_delete_tournament）。只守 sql_delete_tournament_completely 会漏掉 DELETE /tournaments/{id} 路由（它根本不经过 _completely）；反过来只守两条都会调到的底层 sql_delete_tournament 又太迟——级联路径到那一步时 matches 等账本祖先已被删光。删队同理两条：DELETE /teams/{id} 走单删 sql_delete_team（sql/teams.py:121），级联走批量 sql_delete_teams_of_tournament（sql/teams.py:128，非 sql_delete_team）。最稳妥是在赛事级入口（两条删赛事路径的入口 + 删队路由）一并校验 settled_seq；且整段删除应包在单个 transaction 里（避免删一半留下断链）。FK RESTRICT 只作兜底的第二道防线。
删 user 的唯一实路径是 demo 清理 cron，不是交互式删除——守卫语义须随之调整。全仓没有面向用户的删账号路由（routes/ 内无），delete_user_and_owned_clubs（sql/users.py:131）仅被 demo 清理 cron 调用（cronjobs/scheduling.py:25，每 5 分钟清过期 DEMO 账号）。故上文「删 user 入口…要删须先走管理员级撤销结算」措辞在此路径不适用：cron 里没有管理员、也无人看拒绝提示。两点须落地：(1) 该路径守卫须「跳过并告警」而非 raise——run_cronjob 把异常 except Exception 吞掉记 log（scheduling.py:32-35），而 delete_demo_accounts 的 for 循环无内层 try，任一已结算 DEMO 赛事会让整批 demo 删除在该次循环全数中止、并每 5 分钟无限重试；正确形态是逐 tournament 判 settled_seq、命中只跳过该赛事（非跳过整个 user）并发运营告警。注意守卫粒度须按真实的「赛事→俱乐部→账号」间接关系，而非「user 拥有赛事」：赛事无 owner-user 列，只挂 tournaments.club_id（schema.py:24），账号与俱乐部是 M:N（users_x_clubs 带 OWNER/COLLABORATOR 关系）。cron 走 user → get_clubs_for_user_id（sql/clubs.py:55，无 relation='OWNER' 过滤，返回该 user 所属任意俱乐部）→ 俱乐部下所有赛事 → sql_delete_tournament_completely（sql/users.py:132-134）。故守卫须落在该 per-club 循环内的 per-tournament 删除入口，「跳过该 user」既太粗（会滞留本可清的 demo 数据）又无明确语义。(2) 根因修复更稳：在结算路由按「该赛事所属俱乐部是否含 DEMO 成员」门控、禁止其结算（结算本就是管理员级动作；「DEMO-拥有的赛事」在 schema 无直接表示，须经俱乐部成员判定）——否则 DEMO 账号建 rated 个人赛、被结算、30 分钟后 cron 想删它即卡成永不可清的僵尸 demo 账号。（常见路径下 setup_demo_account 给 demo 账号独立俱乐部，跨俱乐部误删今日罕见；但措辞须与 membership-centric 的级联对齐。）

4积分生命周期（关键）

这是本设计最容易出错的地方，单列说明。以一个该类别下全新账号为例：

  1. 进赛：用户申请加入个人赛（或被其托管管理员直接拉入）→ 自动创建同名队伍 + 同名 Player（加入该队）+ 绑定账号。（建 Player 是必需：现模型 Team 1—* Player，选手页 / 赛程 / 统计都依赖队内有 player，空 player 队会让这些页面出错。个人赛即「一队 = 一 Player = 一账号」。）
  2. 预排名设临时初始分：创建者在「队伍预排名」给该无积分账号一个初始分 → player_ratings 建行，status=PENDING，initial_rating=current_rating=X。
  3. 蛇形分组：队伍按各自账号的分（新账号用临时初始分，老账号用正式分）自动排序，据此蛇形分组。此阶段分数只用于排序，不对外计为正式等级分。
  4. 比赛进行：owner / 记分员录比分；引擎可预算出升降（projected）供预览，但不提交到正式分。
  5. 赛事完成 → 创建者点「申请积分结算」：校验「所有队伍已绑账号 + 所有新人已有临时初始分」，通过则进管理员审核队列。
  6. 网站管理员审核：审核本赛事新账号的临时初始分是否合理，可调整后通过（status→ACTIVE，记 approved_by/at）。
  7. 结算（batch）：审核通过后系统给赛事盖一个单调递增的 settled_seq，把整个赛事当一个批次：每场用双方入场前冻结分查表算 delta、求和，写入 rating_events 并更新 current_rating。至此该账号在类别内成为正式选手。
为什么是 batch 而非赛内滚动分：积分赛中本就冻结、赛后才结算，等价于已选 batch。同一赛事内比赛先后顺序不影响结果（每场都用赛前冻结分算差），因此无需记录比赛完成时间。需要顺序的只有赛事之间，而顺序 = settled_seq（结算顺序）。
结算是 append-only：settled_seq 只增不改，晚结算的老赛事只排在最后、不会回头打乱已结算赛事。仅当修改某个已结算赛事的历史比分时，才从它的 settled_seq 往后重放、重建 rating_events。注意此「往后重放」会沿链向后级联到对手（改某账号中段入场分 → 改其后每场 delta → 改对手 delta…），影响范围 = 该类别内该 seq 之后出现过的账号闭包，并非「仅该场参与者」。
结算门槛：要求参与新账号的所有 PENDING 初始分已审核通过；全是老账号（无新人初始分待审）的赛事，创建者点「申请结算」后可直接结算。

引擎设计要点

  • 纯函数 + 可插拔表：backend/bracket/logic/rating/chinatt.py → compute_exchange(winner_rating, loser_rating) -> (winner_gain, loser_loss)。类别 algorithm 字段选表，默认 chinatt。与现有 per-tournament teams.elo_score（Swiss 用的赛事内 ELO，START=1200）是两套独立体系：跨赛事等级分统一叫 rating，不读 / 不写 elo_score，反之亦然，避免混用。
  • batch-per-event（批量结算）：结算一个赛事时，每场都用双方入场前冻结分查表，赛内各场 delta 独立求和——赛内顺序无关，无需完成时间戳。
  • 赛事间按 settled_seq 叠加：类别内以结算顺序为唯一排序真相，append-only。settled_seq 是全局单调序列，同一类别内会有空洞——叠加 / 排序 / 重放都必须先按 category_id 过滤，只在本类别内计算。
  • settled_seq 分配必须防并发：两个管理员可能同时结算两个赛事，必须用 Postgres SEQUENCE 或 SELECT … FOR UPDATE 串行化分配，杜绝重复 / 错序的 seq（seq 是排序真相，错一处全链错）。权衡（暂定保留全局）：选「全局单调、类别内有空洞」是为多类别共用一条时间线；代价是上面反复强调的「叠加/排序/重放都得先按 category_id 过滤」这个 footgun。替代方案是每类别一条独立序列（无空洞、更易推理、去掉该过滤）；二者落地前择一，本设计暂定全局并强制 category 过滤。
  • 结算 / 重放须在单个 transaction 内（防断链）：settled_seq 串行分配只解决排序，不等于原子性。结算是多行多表写（盖 settled_seq+settled_at → 批量写 rating_events → 批量更 current_rating），重放亦然。现有写路径多不带 transaction（如 update_match_by_id 先 sql_update_match 再 recalculate_ranking_for_stage_item，无 database.transaction()；对照 routes/tournaments.py 是有 transaction 的）。故结算 / 重放必须显式整段包进一个 async with database.transaction()——seq 分配 + 全部 rating_events + 全部 current_rating + settled_at 同生共死，中途失败整体回滚，杜绝「写了一半的账本」。
  • 引擎内置自打校验（不止靠 DB 约束）：除 UNIQUE(tournament_id, user_id) 在库层挡「同赛事一账号两队」外，结算 / 重放引擎对每场显式断言 user_id1 ≠ user_id2，命中则跳过并告警。重放 / 管理员级纠错会变动绑定，这条防御性校验避免任何瞬态错绑被算成「自己打自己」（赢家加分与输家减分落在同一 current_rating 上）。但须讲清边界：积分完整性是「按账号」而非「按真人」的——users 只有 email/name（email UNIQUE），无任何「账号 ↔ 真人」绑定。同一个人注册两个账号（或被创建者绑到两支同名队）即可让「自己打自己的两个账号」算出真实 W/L、刷分；user_id1 ≠ user_id2 只挡同一账号别名。Sybil（一人多号）抗性不在本设计范围，须显式文档化；若要防，把去重 / 标记可疑同人挂到既有的「管理员审核临时初始分」闸门（§4 步骤 6）这一天然落点。
  • 幂等 / 可改分：改某已结算赛事的比分 → 从该赛事 settled_seq 往后（且同 category_id）重放、重建 rating_events；正常结算不触发全局重算。重放会向后级联到对手（改某账号中段入场分会改其后每场 delta，进而改对手 delta），影响范围 = 该类别内该 seq 之后出现过的账号闭包。
    matches_played / last_updated 必须「派生」而非「自增」：因重放是从头重建 rating_events（current = initial + Σdelta），若结算时简单 matches_played += n，重放后会漂移失真。故这两列须在同一 transaction 内由 rating_events 重新算出（matches_played = count(该账号的 rating_events)、last_updated 取最新），结算与重放走同一套派生逻辑。（二者不参与 rating 计算——current_rating 纯由 rating_events 导出——故即便写错也只是统计展示失真，非账本错误；但既然便宜，按派生处理一并消除。）
  • 重放成本与运营策略（成熟类别 ≈ 全类别重算）：在成熟类别里「该 seq 之后的账号闭包」实际上≈从该 seq 起的整个类别，故改分纠错代价要正视、不能只挂一个 warning。落地要求：(a) 明确何时才允许改已结算赛事（默认仅管理员级纠错，见 §5，普通改分入口对已结算赛事关闭）；(b) 重放走异步任务 + 类别级锁，避免与新结算 / 其他重放交叉；(c) 重放期间该类别排行榜 / 结算结果标记 stale 或冻结，完成后再发布。这是链式积分的固有代价（入场分逐赛事冻结，后续赛事确实依赖被改赛事结果），非 bug，但须在 UI / 运营上讲清。
  • 提交受门槛控制：仅在 §4 结算阶段提交到 current_rating；之前一律是 projected。

这是本设计改动面最大的一处。 现有授权以俱乐部成员为主（写路径走 get_user_access_to_tournament：users_x_clubs → club → tournament）；读路径已有 user_authenticated_or_public_dashboard 回退——公开赛事（dashboard_public=true）已允许匿名读，GET /tournaments/{id} 等读接口已在用它，仅非公开赛事的读仍受门禁。真正要开口子的是写：scorer / 参赛申请 / 托管管理员都是非俱乐部账号要在别人俱乐部的赛事里写（外加非公开赛事下补读）。这不是「加几张表」，需显式处理：
新主体需要的读权限受影响的现有写入口（要加「OR」分支）
scorer（录分）要能读该赛事（公开赛事已通；仅非公开赛事的读仍受门禁）→ user_can_record_results 同时放行非公开赛事的读所有 match / score 路由（按场录分、改分），逐个改挂 user_can_record_results 而非仅 user_authenticated_for_tournament
申请人 / 自动建队读公开个人赛页（已可匿名看 dashboard）建 team + 绑定：须允许非俱乐部成员在该赛事建队（仅限自己那一支、经批准 / 托管），不能复用「俱乐部成员才能建队」的旧入口
托管管理员同创建者（其本就是某俱乐部成员）跨账号代建队 / 绑定，需校验目标 user 的托管列表命中

落地建议：新增统一依赖 user_can_record_results(tournament_id) = 俱乐部成员 OR tournament_scorers 命中；参赛 / 托管入口单独走 join-request / trusted-manager 校验，不挂俱乐部门禁。P2 / P3 的工作量应按「逐路由改授权」估，而非「加表」。

scorer 授权须自验「match 属于本赛事」，不能信任 match_dependency。新依赖 user_can_record_results(tournament_id) 是按路径里的 tournament_id 授权的，但取 match 走的 match_dependency（routes/util.py:67）有一处既有 bug：where(matches.c.id == match_id and matches.c.tournament_id == tournament_id) 用了 Python 的 and（非 SQLAlchemy 的 &），布尔短路后只剩右操作数、丢掉了 match_id ↔ tournament 的绑定校验（round_dependency:24、team_dependency:84 同样写法）。后果：tournament A 的 scorer 调 /tournaments/{A}/matches/{B 的 match_id} 时，授权按 A 通过、而 match 取到 B 的——可越赛事改分。本设计的 scorer 模型依赖该 scoping。注意修复有个二级陷阱：matches / rounds 表并无 tournament_id 列（match 经 round_id → stage_items → stages.tournament_id 才连到赛事），故朴素的 and → & 改法会引 matches.c.tournament_id KeyError；正确修法是联表 stages 取 tournament_id 作 scoping 子查询（teams 则确有 tournament_id，可直接比较）。本仓库已按此修复 util.py 三处依赖，并通过全部 162 项集成测试。

7关键流程（对应需求）

  1. 申请加入（需求 1）：公开个人赛页 → 登录用户点「申请参赛」，可勾选「信任创建者（加入我的托管管理员）」→ PENDING 进创建者收件箱；批准后自动建同名队伍 + 绑定。若创建者已在该用户托管列表中，则直接拉入、免申请。
    「批准 → 建队 → 绑定」整段须包 transaction，靠唯一冲突触发整个 transaction 回滚（非靠调整插入顺序）。「一账号同赛事最多一队」只靠 teams_x_users 的 UNIQUE(tournament_id, user_id) 兜底，但现有 create_team（routes/teams.py）是无 transaction 的裸 insert、teams 本身无唯一约束，且 join-request 的 UNIQUE 只在申请行上、不在批准动作上。两个几乎同时的批准（或「批准」+「托管直接拉人」并发）会双双通过「是否已是成员」的读、再各自建队 → 第二条绑定虽被 UNIQUE 拒，但队行已插入，留下一支空 player 的孤儿队。故须把批准 / 自动建队 / 建 player / 绑定整段包进单个 async with database.transaction()。修复点是「原子性」而非「插入顺序」：注意 teams_x_users.team_id 是非 DEFERRABLE 的外键（→ teams.id），所以「绑定行先于 team 插」物理上做不到（team 还不存在，FK 立即违例）——除非显式把该 FK 设成 DEFERRABLE INITIALLY DEFERRED，本设计不引入此复杂度。正确形态：同一 transaction 内建 team/player + 插绑定，第二个并发批准在插绑定时撞上 UNIQUE(tournament_id, user_id) 报错 → 整个 transaction 回滚，那条已插的 team/player 行随之撤销、永不提交，孤儿队不复存在。（今天会留孤儿队，正是因为 create_team 此刻没有外层 transaction 兜底。）
  2. 赛事计分设置（需求 2）：赛事设置勾「个人赛」+ 开「参与积分」+ 选类别（默认加华积分 CanadaChinaTT）。积分设置须在建赛时确定：is_individual / rating_category_id 一旦赛事已有队伍 / 比赛便不得翻转——已 populated 的团体赛禁止赛中改成个人赛（无回填路径，且会违反「一队一人」与「全员绑账号」前提），PUT /tournaments 须在此拒绝。
  3. 授权录分（需求 3）：创建者把已绑定账号加入 tournament_scorers。
  4. 初始分 + 升降（需求 4）：创建者预排名设临时初始分 → 蛇形分组；赛后网站管理员审核初始分 → 结算升降（见 §4）；新增类别排行榜页。

11已定事项

  1. 赛内滚动分 vs 批量结算？ 已定 批量（batch-per-event）：赛中冻结、赛后整赛事一批结算，赛内顺序无关、无需完成时间戳；赛事之间按 settled_seq（结算顺序）append-only 叠加。
  2. 全是老账号的赛事是否需管理员确认？ 已定 创建者点「申请结算」后可直接结算（无新人初始分待审时）。
  3. 未绑定账号的队伍如何计分？ 已定 强制全员绑定：rated 个人赛未全员绑账号则不允许结算（拦在「申请结算」入口）。
  4. 托管管理员的代入范围？ 已定 仅允许托管管理员把用户拉进自己创建的个人赛；不支持替用户申请到他人赛事。
  5. 分差恰好落界值时的归属（如 12 / 13 / 37）？ 已定 按官方表闭区间取档：diff ≤ 12、13 ≤ diff ≤ 37…，落地以此为准。
